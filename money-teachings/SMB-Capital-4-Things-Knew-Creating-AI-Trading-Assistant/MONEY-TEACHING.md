# SMB Capital: 4 Things I Wish I Knew Creating AI Trading Assistant

## Overview

This Money Teaching documents four critical mistakes to avoid when building an AI-powered trading assistant with Claude Code. It is based on real-world experience from a retail trader who built an AI trading assistant using Claude Code. The content focuses on moving beyond writing basic implementation code without first documenting the inference architecture, and instead creating a written architecture document structured with defined sections covering purpose, reasoning logic, outputs, rendering, and roadmap, rather than only generating code.

## When to Follow These Money Teachings

- When you want to build a trading assistant, a tool that extracts and combines key points from research sources, or any AI tool that must apply reasoning to identify patterns, themes, and catalysts across data sources
- When you are using Claude Code for a project with more than one functional inference layer (a distinct reasoning task such as morning report synthesis, trade log review, or performance analysis)
- When you need the AI to understand your personal trading process, documented rules for trade entry, exit, and management specific to your strategy, and your systematic approach (a documented set of rules for analyzing markets, identifying opportunities, and managing risk) specific to your strategy
- When you want to avoid: (1) rework within 2 hours of market open that causes you to miss the market open, (2) mixing architecture design with code implementation in the same chat session, including across tabs within that session, (3) the model generating plausible-sounding but factually incorrect themes, catalysts, or analysis not present in source data, and (4) conflicting directives given across separate sessions that the model cannot simultaneously satisfy

## Steps

### Step 1: Build an inference architecture into the application to reason over data at runtime, with separate components for input processing, inference, and output generation (Not Just a Code Factory)

Do not treat Claude Code as a tool that only writes code when prompted. Instead, integrate Claude's ability to synthesize information, draw inferences, and apply context from the architecture document and user settings to new data directly into the application when new unprocessed data arrives after the last inference run or when the user requests a morning report, trade log review, or performance analysis. Design the application so the Large Language Model (LLM) analyzes data and provides catalyst alerts, risk warnings, or opportunity flags at runtime (not buy/sell orders) rather than only generating code during development. The LLM must not submit, place, or transmit any order to a brokerage API, and the application must not allow the LLM to modify the application's code. Define an inference architecture where the app uses the language model to extract and combine catalysts, themes, and trade-relevant events from emails, analyst reports, Edgar filings, market filters, macro trends, and pre-market data by identifying the driver, magnitude, timeline, and affected tickers of each catalyst, highlight relevant catalysts and events, and analyze each catalyst's component parts, and review performance against your systematic approach to analyzing markets, identifying opportunities, and managing risk.

### Step 2: Use Separate Chat Sessions for Each Inference Layer

Never run the entire project inside a single Claude Code session. As a single chat session runs for an extended period (excluding code blocks and file contents), the model may show (1) inconsistency across prompts (outputs that conflict with earlier outputs), (2) contradictions between earlier and later instructions, and (3) factual errors in outputs (claims not supported by source data). Create separate chat sessions for each functional unit; do not use tabs within a single session to maintain active context for multiple functional units, where each functional unit performs one function (e.g., morning report synthesis, trade log review, performance analysis) of your trading assistant. For example, have one chat for the morning report synthesis, one for the trade log review, and one for the performance analysis. Keep the Claude Code session for implementation only, and do all architecture and reasoning design in the dedicated Claude Code or Claude.ai chat sessions, not tabs within a single session.

### Step 3: Create a Per-Layer Architecture Document and Close the Loop

Coding without architecture documentation leaves scattered notes, comments, and decisions that contradict each other and create confusion in the codebase. For each functional unit that produces a unique output format or workflow separate from the others (e.g., morning report synthesis, trade log review, performance analysis), create a written architecture document that serves as the only authoritative specification that overrides all other notes, comments, and prior instructions; when code contradicts the document, refactor the code to match the document. The document should cover: A) system purpose, B) how the system thinks, C) what the system produces, D) how it is rendered and run, and E) phase two roadmap. Update the architecture document first with every behavioral or structural refinement (changes to data models, Application Programming Interface (API) contracts, component boundaries, or system topology). UI styling, font changes, and color adjustments do not require architecture updates, while changes to rendering (e.g., changing a table to a chart) do require updates. Then prompt Claude Code with the updated architecture attached and ask it to report what in the codebase does not align with the architecture. Adjust both until every behavior described in the architecture document has a corresponding implementation, and every implementation serves a documented purpose. This practice is called "closing the loop," which means after implementing changes, prompt Claude Code to report what in the codebase does not align with the architecture, then refactor the codebase to match the architecture document.

### Step 4: Teach Your Assistant Who You Are via a Settings Tab

An AI that knows nothing about your process is likely to produce output that does not match your approach or includes irrelevant themes and catalysts. Build a persistent configuration interface (web form, config file, or database table) that injects user context into the inference engine inside your trading assistant on each inference request. Include: your documented trading rules for trade entry, exit, and management specific to your documented trading playbook; a trade table template with columns for date, trade grade, Profit and Loss (P&L), and process adherence score (a score from 1-10 where each documented rule violation deducts 1 point, with a minimum score of 0; if violations exceed 10, the score is capped at 10, and violations exceeding 10 are logged separately); risk parameters (maximum position size, stop-loss distance, and daily loss limit); a rubric for rating catalyst significance (e.g., 1-5 scale; define your own thresholds for each level in your settings); your documented evaluation checklist for evaluating each trade; labels, sizes, and risk parameters (maximum position size, stop-loss distance, and daily loss limit) for each trading account you manage; for each theme: a unique name, a one-sentence definition, inclusion criteria, and exclusion criteria; assign each ticker to the most specific applicable theme when themes overlap; and a structured list (CSV, JSON, or database table) mapping tickers to themes with dates; allow multiple rows per ticker-date for many-to-many mappings. The more explicit inclusion/exclusion rules you provide, the more accurately Claude can apply reasoning, though results are not guaranteed. Without this context, the assistant may hallucinate themes, misfile catalysts, and ignore your systematic approach to analyzing markets, identifying opportunities, and managing risk.

## Examples

### Example 1: Morning Report Synthesis

Instead of asking Claude to "make a morning report," define inference architecture: the application uses an LLM to reason over data at runtime, with separate components for input processing, inference, and output generation. The settings tab has four sections: environment, themes, catalysts, and watch list. For the environment section, instruct Claude to answer by describing market conditions and trading context: "What is the market state (trending, range-bound, or volatile)?" For the catalyst section, instruct Claude to answer: "What names have the most significant catalysts according to your rubric?" by starting from individual company-specific catalysts rather than market-wide trends. Provide your catalyst scoring system and theme definitions in the settings tab. The result is a report that displays catalysts in ranked order with ticker, catalyst type, significance score, and source email, and themes that match your documented trading approach.

### Example 2: Trade Log and Performance Review

Build a functional unit of the application that performs one type of inference (e.g., morning report synthesis, trade log review, performance analysis). This unit asks questions with constrained answer formats (Yes/No, ticker symbol, numeric score, date range) about each trade and asks follow-up questions to clarify entries lacking specifics on catalyst, grade, or execution rationale. Build a second performance layer that groups outcomes by trade grade, catalyst type, or market condition and computes frequency and average P&L. The daily log layer reviews individual trades. The performance layer identifies recurring outcomes grouped by trade grade, catalyst type, or market condition over a defined time period. Feed both layers your review process and performance grading table from the settings tab so the AI understands your trading mistakes.

## Best Practices

- ✅ Design the inference architecture into the application to reason over data at runtime, with separate components for input processing, inference, and output generation before writing implementation code for the inference layer
- ✅ Keep one chat session per functional unit of the application that performs one function (e.g., morning report synthesis, trade log review, performance analysis) and never mix architecture design with code implementation in the same chat session, except when a code change reveals a structural requirement that must be captured in the architecture document before proceeding
- ✅ Maintain a written architecture document as the only authoritative specification that overrides all other notes, comments, and prior instructions
- ✅ Close the loop by prompting Claude Code to list all public interfaces, user-facing features, and major internal components and their purposes, then compare each feature's behavior against the architecture document's specifications after every behavioral or structural change
- ✅ Store the following in a settings tab: (1) your documented trading rules for trade entry, exit, and management specific to your documented trading playbook; (2) a trade table template with columns for date, trade grade, Profit and Loss (P&L), and process adherence score (a score from 1-10 where each documented rule violation deducts 1 point, with a minimum score of 0; if violations exceed 10, the score is capped at 10, and violations exceeding 10 are logged separately); (3) risk parameters (maximum position size, stop-loss distance, and daily loss limit); (4) a rubric for rating catalyst significance (e.g., 1-5 scale; define your own thresholds for each level in your settings); (5) your documented evaluation checklist for evaluating each trade; (6) labels, sizes, and risk parameters (maximum position size, stop-loss distance, and daily loss limit) for each trading account you manage; (7) for each theme: a unique name, a one-sentence definition, inclusion criteria, and exclusion criteria; assign each ticker to the most specific applicable theme when themes overlap; and (8) a structured list (CSV, JSON, or database table) mapping tickers to themes with dates; allow multiple rows per ticker-date for many-to-many mappings.
- ✅ Lead prompts with a description of the target output including structure, content, and criteria for inclusion, not a list of steps
- ✅ Verify output against source data by checking a list at the bottom of each report section linking each claim to the exact email, report, or data record (by filename, date, and sender)

## Keep In Mind

- As a Claude Code session runs for an extended period, context degrades and contradictions accumulate
- Vibe coding is fine for isolated visual adjustments limited to appearance such as font size or color changes, provided they can be verified by visual inspection alone without altering data flow, state transitions, or Application Programming Interface (API) contracts, but not recommended when building a feature that processes data or alters application behavior
- If removing any single criterion does not change the expected output, the boundary is not specific enough. The AI may generate plausible but incorrect themes and catalysts not in your theme database
- The architecture document should be updated first, then Claude Code should implement the changes
- When the project has more than one inference layer, ensure Claude Code reads claude.md in the project root that contains persistent instructions, conventions, and architecture context at the start of every session; update the markdown file whenever the architecture document changes

## Security & Safety Notes

- Do not expose raw API keys or credentials inside the architecture document or settings tab
- Treat the architecture document as confidential information that encodes your specific trading process
- Audit every report generated by the trading assistant, verifying each source citation (the list linking claims to emails, reports, or data records) before using the output to make a trading decision or sharing with anyone outside your personal use
- Start with non-real-money testing until reports consistently pass manual source verification, where each claim in the report must be traceable to a specific source citation and no citation may reference data not present in the source, before using the output to make a trading decision or sharing with anyone outside your personal use

## Common Pitfalls

- **Problem:** Using Claude Code only to write functions and never making API calls to the LLM from application code, passing data and context, and processing returned reasoning
  **Solution:** Build an inference architecture into the application. This architecture should reason over data at runtime using separate components for input processing, inference, and output generation. The LLM, running inside the application, applies the reasoning patterns defined in your architecture document and user settings to each new data point at runtime to draw inferences within the bounds defined in your architecture.

- **Problem:** Running the entire project in a single Claude Code session
  **Solution:** Use separate chat sessions, not tabs within a single session for each functional unit of the application that performs one function (e.g., morning report synthesis, trade log review, performance analysis) and keep Claude Code for implementation only

- **Problem:** Coding without a documented architecture leads to contradictions and unreconciled instructions in many initial builds, particularly for projects with multiple inference layers.
  **Solution:** Write a per-layer architecture document and close the loop after every behavioral or structural refinement to an inference layer. Simple UI tweaks such as font size or color changes do not require architecture updates or loop closure.

- **Problem:** Giving the AI context that lacks your trading rules, risk parameters, catalyst methodology, and theme definitions, causing output that lacks your specific themes and catalysts or contains claims not traceable to source data
  **Solution:** Populate a settings tab with: (1) your documented rules for trade entry, exit, and management, all specific to your strategy; (2) a trade table template with columns for date, trade grade, Profit and Loss (P&L), and process adherence score (a score from 1-10 where each documented rule violation deducts 1 point, with a minimum score of 0; if violations exceed 10, the score is capped at 10, and violations exceeding 10 are logged separately); (3) risk parameters (maximum position size, stop-loss distance, and daily loss limit); (4) catalyst methodology (e.g., your seven-step catalyst breakdown with defined buckets and thresholds) for analyzing markets and identifying opportunities; (5) your documented evaluation checklist for evaluating each trade; (6) labels, sizes, and risk parameters (maximum position size, stop-loss distance, and daily loss limit) for each trading account you manage; (7) for each theme: a unique name, a one-sentence definition, inclusion criteria, and exclusion criteria; assign each ticker to the most specific applicable theme when themes overlap; and (8) a structured list (CSV, JSON, or database table) mapping tickers to themes with dates; allow multiple rows per ticker-date for many-to-many mappings.
